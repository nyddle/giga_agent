# Agentic-бенчмарк: GigaAgent без/с markitdown (фаза 1)

**Вопрос:** улучшает ли markitdown работу *агента целиком* на задачах
«прочитай приложенный офисный файл с таблицей и ответь»?

## Методика

- **Объект:** харнес GigaAgent — парсеры, маршрутизация файлов, агентский цикл. Модель внутри пары условий фиксирована: **gpt-4o** (llm_id пользователя на момент прогона; изначально в отчёте ошибочно значился GigaChat-2-Max — исправлено по usage-журналу). A/B сравнивает версии харнеса, а не модель через живой
  чат-API (`upload → thread → runs/wait`, `auto_approve`). Не «голая модель».
- **A/B:** одна кодовая база, переключатель `GIGA_AGENT_MARKITDOWN` (off = старые
  парсеры: python-docx/plain, PPTX не читается; on = markitdown). Контейнер
  пересоздавался между условиями; единственная переменная — парсер вложений.
- **Корпус:** 30 вопросов (стратифицированно из 88): WikiTableQuestions
  (валидированные эталоны) + русская синтетика; файлы DOCX/PPTX, таблицы ≤14×7.
- **Повторы:** ×3 на вопрос (GigaChat недетерминирован), 90 ранов на условие.
- **Скоринг:** strict (эталон входит в ответ / числовое равенство) и lenient
  (+ ответ-подмножество слов эталона: «Roberts» ≈ «Calvin Roberts»).
- **Метрики агента:** вызовы модели на задачу (из usage-журнала), суммарные
  токены, латентность e2e. Транзиентные сбои песочницы помечены отдельно.

## Результаты (A = без markitdown → B = с markitdown)

| Срез | acc strict | acc lenient | латентность (med) | токены/ран (med) | вызовов модели |
|---|---|---|---|---|---|
| docx/en | 71% → 71% | 83% → 79% | 22s → 34s | 18.6K → 18.6K | 2 → 2 |
| docx/ru | **100% → 100%** | 100% → 100% | 33s → 33s | 18.4K → 18.4K | 2 → 2 |
| pptx/en | **0% → 29%** | **0% → 46%** | 48s → 34s | 23.2K → 18.5K | 2 → 2 |
| pptx/ru | **0% → 62%** | **0% → 62%** | **54s → 35s** | **38.0K → 18.4K** | **4 → 2** |
| **ИТОГО** | **42% → 64%** | **46% → 71%** | | | |

Транзиенты стенда (SandboxBusy и т.п.): A — 5 ранов, B — 1 ран; помечены, не
исключены (консервативно занижают обе стороны).

## Выводы

1. **PPTX — категорический прирост.** Без markitdown агент не может прочитать
   презентацию: 0% на 36 ранах. Наблюдаемое поведение бейзлайна — лишние
   итерации (4 вызова модели вместо 2 на pptx/ru), **вдвое больше токенов**
   (38K против 18.4K) и в полтора раза дольше — и всё равно отказ. markitdown
   превращает это в обычный однопроходный сценарий.
2. **DOCX на компактных таблицах — паритет.** Старый парсер склеивает ячейки
   через ` | `, и на таблицах ≤14×7 модели этого достаточно (docx/ru: 100%
   у обоих условий на gpt-4o). Опубликованные +6–9% для markdown-таблиц на
   этом корпусе не воспроизводятся; для GigaChat вопрос открыт — не измеряли.
3. **Экономика инференса:** там, где бейзлайн падает, он падает дорого.
   Выигрыш markitdown в agentic-метриках — не только accuracy, но и
   стоимость/латентность провальных траекторий.

## Ограничения

- Таблицы корпуса компактные (ограничение рендера) — эффект markdown-структуры
  на больших/сложных DOCX-таблицах не измерен; вероятно, там дельта появится.
- XLSX-вложения не тестировались (путь не менялся — уходят в REPL/pandas).
- RAG-блок (инжест в базы знаний) не гонялся: для PPTX/XLSX прирост
  категориален по построению (форматы ранее не принимались).
- Модель — gpt-4o: выводы о харнесе (доступность форматов, цена траекторий)
  переносимы; модельно-чувствительные детали (величина docx-дельты) — нет.
- pptx/en strict занижен артефактом скоринга (короткие ответы-фамилии);
  lenient ближе к реальности.

## Воспроизведение

```bash
python bench/build_corpus.py                                   # корпус + golden
GIGA_AGENT_MARKITDOWN=off … python bench/agentic_bench.py --condition A --limit 30 --repeats 3
GIGA_AGENT_MARKITDOWN=on  … python bench/agentic_bench.py --condition B --limit 30 --repeats 3
```

# Дополнение: XLSX-вложения — REPL vs markdown-контекст (фаза 2, эксперимент)

**Гипотеза:** для небольших XLSX прямое чтение в контекст (markitdown через
read_file) надёжнее и дешевле, чем штатный путь «иди в python/pandas».

**Сетап:** тот же харнес и стенд; модель фиксирована и записана в каждом ране
(gpt-4o-2024-08-06, ассерт по usage-журналу). 16 вопросов WTQ × 2 повтора на
условие. X-repl = штатный путь (подсказка «используй python»); X-md =
GIGA_AGENT_MARKITDOWN_XLSX=on (read_file отдаёт markdown-таблицу, ≤100KB)
+ подсказка в file_prompt.

| метрика | X-repl | X-md |
|---|---|---|
| accuracy strict | 16% | **66%** |
| accuracy lenient | 22% | **78%** |
| читал файл | 28/32 | **32/32** |
| вызовы модели med/max | 3 / 6 | **2 / 2** |
| токены/ран (med) | 27,966 | **18,622** |
| латентность med | 45s | **4s** |

**Выводы.**
1. REPL-путь на малых таблицах ненадёжен даже у gpt-4o: агент пишет pandas-код
   по файлу, которого не видел (угадывает колонки), делает до 6 итераций и
   чаще всего ошибается. 16% — воспроизводимое число (два независимых прогона).
2. Контекст-путь ведёт себя как DOCX-сценарий: детерминированные 2 вызова,
   −33% токенов, латентность на порядок ниже, точность ×4 (strict).
3. Остаточные промахи X-md — в основном артефакты скоринга (ответ «Roberts» на
   эталон «Calvin Roberts», русский «Менее.» на эталон «less»).

**Рекомендация (дизайн фазы 2):** роутинг XLSX-вложений по размеру — маленькие
(≲100KB) в контекст через markitdown, большие — как сейчас в REPL/pandas.
Механика уже реализована за флагом GIGA_AGENT_MARKITDOWN_XLSX.

**Инцидент-лог честности:** первые прогоны пары были инвалидированы (застрявшая
песочница; захардкоженный путь хоста в docker-compose.dev.yml, чинится в этой
ветке; смерть квоты OpenAI посреди прогона). После починки стенда и добавления
в харнес записи модели + стоп-гарда пара перегнана начисто.
